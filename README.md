# Отпуска команды — 2027

Внутренний сервис планирования отпусков для одной доверенной команды.
Каждый входит по имени (без регистрации и паролей), отмечает свои дни отпуска
на календаре 2027 года и видит дни коллег.

## Возможности

- Вход по имени и фамилии: `Пётр` + `Фёдоров`, `петр` + `федоров` и `  ПЁТР ` + ` ФЁДОРОВ `
  — один и тот же пользователь.
- Календарь на весь год, неделя с понедельника, выходные выделены визуально
  (на подсчёт дней это не влияет — выходные считаются как обычные дни отпуска).
- Нерабочие праздничные дни выделены отдельным цветом. Праздник можно отметить,
  но в количество дней отпуска он не попадает.
- У каждого участника видна разбивка засчитанных дней по месяцам.
- Клик по дню переключает его, Shift + клик выделяет диапазон.
- Несохранённые изменения видны отдельно (штриховка — добавлено, зачёркнуто — удалено)
  и применяются одной кнопкой «Сохранить».
- Дни коллег показаны цветными точками, при наведении — список имён.
- Любой участник может переименовать или удалить любого: команда доверенная,
  аутентификации нет сознательно.
- Данные обновляются раз в минуту и при возвращении на вкладку; свой черновик не теряется.

## Требования

- Node.js 22 LTS (сборка проверена и на 24).
- Для продакшена — Docker и Docker Compose.
- Для `scripts/backup.sh` — утилита `sqlite3` (в контейнере уже установлена).

## Запуск локально

```bash
npm install
npm run dev
```

Откроется два процесса:

- Vite dev server — http://localhost:5173 (интерфейс, запросы `/api/*` проксируются на Fastify);
- Fastify — http://localhost:3000 (API, база в `./data/vacations.db`).

Работать нужно с http://localhost:5173.

Прочие команды:

```bash
npm test          # все тесты (unit, API через fastify.inject, логика черновика)
npm run typecheck # проверка типов сервера и клиента
npm run build     # сборка сервера в dist/server и SPA в dist/web
npm start         # запуск собранного приложения (один процесс отдаёт API и статику)
```

## Конфигурация

| Переменная      | По умолчанию            | Значение                                    |
| --------------- | ----------------------- | ------------------------------------------- |
| `PORT`          | `3000`                  | Порт HTTP-сервера                           |
| `DB_PATH`       | `./data/vacations.db`   | Путь к файлу SQLite                         |
| `VACATION_YEAR` | `2027`                  | Единственный год, с которым работает сервис |

Переключения года в интерфейсе нет: год задаётся только этой переменной.

## Деплой на свой сервер

1. Скопируйте проект на сервер (`git clone` или `rsync`).

2. **Если вы обновляете уже работающий сервис — сбросьте базу**, см.
   «Сброс базы перед обновлением» ниже. В этой версии изменилась схема таблицы `users`
   (имя и фамилия хранятся отдельно), а переноса старых данных нет.

3. Поднимите сервисы:

   ```bash
   docker compose up -d --build
   ```

   Поднимается два контейнера: `app` (Fastify, отдаёт API и собранный SPA)
   и `caddy` (reverse proxy на `app:3000`).

4. Откройте `http://<IP-сервера>` — сервис работает по HTTP по адресу сервера.
   В `Caddyfile` указан `:80`, то есть Caddy отвечает на любой адрес и ничего
   не перенаправляет на HTTPS. Отдельный домен не нужен.

5. Проверьте состояние:

   ```bash
   docker compose ps          # app должен быть healthy
   curl -fsS http://<IP-сервера>/api/health
   docker compose logs -f app
   ```

### Дополнительно: свой домен и HTTPS

Если сервису нужен домен с сертификатом, замените в `Caddyfile` строку `:80`
на своё доменное имя:

```caddy
vacations.example.com {
	encode zstd gzip
	reverse_proxy app:3000
}
```

Домен должен A-записью указывать на сервер, а порты 80 и 443 быть доступны снаружи —
Caddy сам получит и будет продлевать сертификат Let's Encrypt. После правки:

```bash
docker compose restart caddy
```

### Данные и обновление

База лежит в `./data` на хосте (том примонтирован в контейнер).
Контейнер работает от непривилегированного пользователя `node` (uid 1000),
поэтому каталог должен быть ему доступен на запись:

```bash
sudo chown -R 1000:1000 ./data
```

Обновление версии:

```bash
git pull
docker compose up -d --build
```

Миграции применяются автоматически при старте приложения.

### Сброс базы перед обновлением

Схема `users` в этой версии изменилась: вместо одного `display_name` хранятся
`first_name` и `last_name`. Миграции переноса данных нет — схема изменена
в начальной миграции, поэтому старый файл базы нужно удалить вручную.
Иначе приложение не найдёт новых колонок.

```bash
cd /opt/vacations                 # каталог с docker-compose.yml
docker compose down               # остановить сервисы
cp ./data/vacations.db ./data/vacations.db.old 2>/dev/null || true   # если нужен старый файл
rm -f ./data/vacations.db ./data/vacations.db-wal ./data/vacations.db-shm
docker compose up -d --build      # стартует с пустой базой и новой схемой
```

После старта база пустая: все заходят заново, указывая имя и фамилию.

Для локальной разработки то же самое:

```bash
rm -f ./data/vacations.db ./data/vacations.db-wal ./data/vacations.db-shm
```

## Бэкап и восстановление

### Бэкап

`scripts/backup.sh` делает консистентную копию через `sqlite3 ".backup"` —
её можно снимать на работающем сервисе, не останавливая контейнер.
Копии складываются в `./backups` с датой в имени, хранятся последние 30.

С хоста (нужен установленный `sqlite3`):

```bash
DB_PATH=./data/vacations.db ./scripts/backup.sh
```

Через контейнер (`sqlite3` уже внутри, ничего ставить не нужно):

```bash
docker compose exec app bash scripts/backup.sh
```

В этом случае копии появятся в `/app/data/backups`, то есть в `./data/backups` на хосте.

Переменные: `DB_PATH`, `BACKUP_DIR` (по умолчанию `./backups`), `KEEP` (по умолчанию 30).

### Cron

Ежедневная копия в 3:30 ночи — строка для `crontab -e`:

```cron
30 3 * * * cd /opt/vacations && /usr/bin/docker compose exec -T app bash scripts/backup.sh >> /var/log/vacations-backup.log 2>&1
```

Либо, если `sqlite3` установлен на самом хосте:

```cron
30 3 * * * cd /opt/vacations && DB_PATH=./data/vacations.db ./scripts/backup.sh >> /var/log/vacations-backup.log 2>&1
```

### Восстановление

```bash
docker compose stop app
cp ./data/vacations.db ./data/vacations.db.broken        # на всякий случай
rm -f ./data/vacations.db ./data/vacations.db-wal ./data/vacations.db-shm
cp ./backups/vacations-2027-03-01_03-30-00.db ./data/vacations.db
sudo chown 1000:1000 ./data/vacations.db
docker compose start app
```

Файлы `-wal` и `-shm` удаляются намеренно: они относятся к старой базе,
а копия уже содержит все завершённые транзакции.

## Праздничные дни

Нерабочие праздничные дни одинаковы из года в год и применяются к `VACATION_YEAR`.
Список лежит в `shared/holidays.ts` и используется и сервером, и клиентом:

| Дата | Праздник |
| --- | --- |
| 1–6 и 8 января | Новогодние каникулы |
| 7 января | Рождество Христово |
| 23 февраля | День защитника Отечества |
| 8 марта | Международный женский день |
| 1 мая | Праздник Весны и Труда |
| 9 мая | День Победы |
| 12 июня | День России |
| 4 ноября | День народного единства |

Правила:

- Праздничный день **можно отметить** — он сохраняется как обычный день отпуска,
  но **не засчитывается** в количество дней.
- Выходные (сб, вс) засчитываются как обычные дни.
- Если праздник выпал на выходной, он показывается как праздник и не засчитывается.
- Переносы выходных не реализованы.
- Счётчик «Несохранённых изменений» считает все правки, включая праздничные дни:
  это количество изменений, а не дней отпуска.

Чтобы изменить список праздников, правьте `HOLIDAYS` в `shared/holidays.ts` —
пересчёт на сервере и в интерфейсе подхватится автоматически.

## API

Все ответы в JSON, ошибки — `{ "error": { "code": "...", "message": "..." } }`.

| Метод    | Путь                   | Назначение                                                  |
| -------- | ---------------------- | ----------------------------------------------------------- |
| `GET`    | `/api/health`          | `{ ok: true }`, используется healthcheck'ом                  |
| `POST`   | `/api/users`           | Вход или создание по `{ firstName, lastName }`: 200 (`created: false`) / 201 |
| `GET`    | `/api/users/:id`       | Пользователь; 404 `USER_NOT_FOUND`                           |
| `GET`    | `/api/calendar`        | Год и все пользователи с днями, отсортированы по имени       |
| `PUT`    | `/api/users/:id/days`  | Замена набора дней; 409 `VERSION_CONFLICT`, 400 `INVALID_DATE` |
| `PATCH`  | `/api/users/:id`       | Переименование по `{ firstName, lastName }`; 409 `NAME_TAKEN` |
| `DELETE` | `/api/users/:id`       | Удаление (дни каскадом); 204                                 |

Пользователь в ответах содержит `firstName`, `lastName` и вычисляемый
`displayName` («Имя Фамилия»). Уникальность — по нормализованной паре имя+фамилия
(trim, схлопывание пробелов, нижний регистр, ё→е), поэтому `Пётр Фёдоров`
и `петр федоров` — один и тот же пользователь. Имя и фамилия обязательны,
каждое от 1 до 30 символов.

Поле `dayCount` в `GET /api/calendar` — количество **засчитанных** дней отпуска:
праздничные дни в него не входят (см. ниже), выходные входят.

Сохранение дней защищено оптимистичной блокировкой: клиент присылает `version`,
которую получил last; если она разошлась с серверной, приходит 409 вместе
с актуальным состоянием пользователя.

## Структура проекта

```
shared/   Zod-схемы, типы, нормализация имени, даты, праздники и подсчёт дней, палитра —
          общее для клиента и сервера
server/   Fastify: роуты, чистый SQL поверх better-sqlite3, миграции, тесты API
web/      React + Vite: календарь, список пользователей, логика черновика
scripts/  backup.sh и копирование миграций в dist
```

В продакшене один процесс Fastify отдаёт и API (`/api/*`), и собранный SPA.
